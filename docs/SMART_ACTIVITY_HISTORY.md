# Fix #6 — tank activity and automation history

Audit and Web implementation: 2026-10-11. Supabase project:
`abtzkqfrwzcocyrwcrfc`. Remote inspection was read-only. No migration, data
backfill, firmware change, Git push or deployment was performed.

## Existing storage and missing evidence

No duplicate `activity_logs` table is needed. The existing Tank Details Activity
tab previously showed `device_commands` and threshold updates only, with a
global history cap before tank filtering and raw status badges. It did not
bring together sensor alerts, manual ammonia results or raw automation reasons.

The live schema and aggregate event audit verified:

| Source | Available information | Limitation |
| --- | --- | --- |
| `device_commands` | Feeding/refill/drain requests, statuses, result text, created/updated/executed times | `done` alone is not execution evidence; mirrored automation maps unknown statuses to `done` |
| `tank_automation_logs` | `AUTO_DRAIN`, `AUTO_REFILL`, reasons, recorded sensor statuses, durations | RLS is disabled; do not expose this table through a new direct frontend query |
| `control_logs` | Eleven threshold updates with saved old/new values, scope/source and notes at audit time | Other action categories are supported but were not present in this audit |
| `alerts` | Recorded sensor Warning/Critical transitions and action notifications | No audited sensor event has a saved `sensor_snapshot`; no recovery or device connection event types were present |
| `ammonia_readings` | Independent dated manual results, saved classifications and optional related alert | Manual history is not live sensor evidence |
| `iot_devices` | Current connection/last-seen state | A current state does not establish a historical connect/disconnect event |

Sensor alerts are generated by the existing reading trigger on firmware status
transitions. This implementation does not create entries for individual sensor
uploads. Alert preferences can suppress event creation. Existing alert rows may
also be edited/resolved by other code; this UI cannot recover a missing original
snapshot or turn mutable historical storage into an immutable audit trail.

Local actuator source inspection found:

- Manual commands report `running`, then `done` / `failed` / `rejected` with a
  result message; final statuses also send `executed_at` from the device clock.
- Water-correction automation inserts a result after its command-cycle return
  value. A trigger mirrors that row into a command, preserving `Auto log id` in
  its result text but losing some original outcomes.
- The scheduled feeding path and several unsafe skips are printed to Serial
  rather than inserted into a backend history table. No historical entries are
  fabricated for these paths.
- There is no flow sensor or feed-delivery confirmation in the inspected
  contract. A reported completed relay/servo cycle does not establish delivered
  water volume or dispensed feed.
- Device writes currently use anonymous project access, not a distinct verified
  device identity. No credentials were copied or changed in this task.

## Implemented Web behavior

The existing Tank Details **Activity** tab now has a responsive timeline,
activity-type filter, inclusive Philippine start date/exclusive next-day end
date, pagination, refresh, partial-read notices, retry and a truthful empty
state. Tank selection continues through the existing tank navigation.

Each available record displays tank name, activity type, saved severity or
appropriate outcome, title, recorded reason, reading/unit and saved threshold
snapshot when present, requested action, result and Asia/Manila observation
time. Metadata fields are optional; absent evidence stays absent.

The portable normalizer accepts saved event rows only. It does not load current
thresholds or evaluate historical readings using today's settings. Threshold
change notes remain their saved old/new values. Sensor recommendations reuse
Fix #4's parameter-specific inspection guidance, explicitly labeled **Inspection
guidance** rather than pretending the advice was recorded at event time. A
saved recommendation action, when provided, is labeled **Recorded recommendation**.
No Fix #5 implementation was available to integrate.

Outcomes are Requested, Started, Completed, Skipped, Failed, or Unknown /
Unconfirmed. Equipment completion needs the recognized inspected firmware
acknowledgement (final status, result contract and valid acknowledgment time)
or the specific recorded automatic water-correction completion contract.
Default `completed`/`done`, arbitrary metadata flags, orphan completed-looking
notifications and lossy mirrored automation statuses cannot establish completion.
Threshold saving is a completed database action, distinct from hardware execution.
Rejected/blocked/cancelled commands appear as Skipped with their original reason.
The Tank Details Latest Action summary uses the same acknowledgement rule;
raw `done` no longer produces a successful-completion claim there either.

Completion is always a **reported command-cycle result**, not independently
measured physical execution or cryptographic device attestation. Existing
anonymous write access remains a trust limitation until the backend/device
security work below is approved and completed.

Only explicitly recorded recovery events are shown as recovery. An alert marked
handled/resolved is not evidence that the sensor recovered. Connection events
are shown only if they were actually recorded as events.

Ordering uses the database record's `created_at`, never device timezone,
`Date.now()`, fabricated timestamps or the device-supplied `executed_at` for
chronology. A command entry represents its latest recorded outcome against its
original request/record time; the database does not store every intermediate
command-status transition. Missing/ambiguous timestamps display unavailable
and sort last.

Source IDs are deduplicated. Explicit command/control/ammonia alert links and
the automation mirror's `Auto log id` remove duplicate representations. Similar
values or titles alone are not enough to merge independent real events.
Polling replaces the snapshot rather than appending it. All reads verify the
authenticated owner and selected tank; queries filter by both before pagination.
Each source is paged in batches of 100 up to 1,000 rows, with an explicit notice
and date narrowing for capped histories. No raw sensor-history query or event
write is introduced.

While open the timeline refreshes every 30 seconds, on focus, and after settings
events. Requests are versioned and cancelled on filter/tank changes or unmount;
a 15-second timeout bounds the visible loading state. Failed sources are
identified while verified sources remain available; total failure is an error,
not an empty-success result. Missing automation RPC is remembered to avoid
repeated polling failures; explicit refresh retries detection.

## SQL prepared for review — not applied

Candidate:
[`sql/20261011190000_tank_activity_history_review.sql`](sql/20261011190000_tank_activity_history_review.sql).

It adds:

```sql
public.get_tank_automation_history(
  p_tank_id uuid,
  p_from timestamptz DEFAULT NULL,
  p_to timestamptz DEFAULT NULL,
  p_offset integer DEFAULT 0,
  p_limit integer DEFAULT 100
) RETURNS SETOF public.tank_automation_logs
```

The read-only SECURITY DEFINER function uses an empty search path, explicit
schema references, verified `auth.uid()`, owned-tank validation, owner/tank row
filters, bounded pagination and authenticated-only execution. Existing broad
authenticated SELECT policies on `control_logs` and `device_commands` are
intersected with restrictive owner/tank read guards. Three owner/tank/date
indexes support the queries. Unneeded TRUNCATE/TRIGGER/REFERENCES privileges on
these history sources are revoked from public application roles. No event
rows, thresholds, legacy settings or device command writes are changed.

The RPC does not exist remotely yet. Until this reviewed SQL is applied, Web
shows an explanatory notice, the existing mirrored command records and the
other verified sources. It never falls back to a direct unrestricted
`tank_automation_logs` read.

**Remote privacy/security acceptance is not complete.** The audit found broad
authenticated command/control SELECT policies, anonymous command read/update
policies, RLS disabled on automation history and broad table grants. Browser
owner filters cannot secure those endpoints against manually modified requests.
The candidate improves authenticated reads and provides the owner-checked RPC,
but anonymous raw device endpoints remain accessible. A coordinated backend
device-authentication gateway and grant/RLS review is needed before revoking
those paths, to avoid breaking the working ESP32. This task does not claim to
have secured device identity or all database access.
